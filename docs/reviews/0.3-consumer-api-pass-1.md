# Water Chemistry Engine 0.3 Consumer API — Pass 1 Review

This record summarizes the independent discovery review of the first 0.3
consumer-API slice. The reviewer assessed the exact range
`65a11fe423053b7a19c4a099c1ad234f22455da0..4cab4f2135feeadad352e2d2d8be242eb4272fb3`
from a fresh clone without modifying the repository.

The reviewer read the complete change and its reachable implementation,
verified the GitHub Actions run, ran all 387 tests on Python 3.11 through 3.13,
ran Ruff and strict mypy, built and installed the wheel outside the checkout,
executed the documented example, independently checked its gypsum
stoichiometry, and probed pH-unit and unknown/bounded-value behavior. No
scientific, numerical, packaging, installation, import-cycle, or Python 3.11
defect was found.

This is a point-in-time audit artifact, not a normative specification. A
focused follow-up review is still required after remediation.

## Findings and adjudication

### F1 — P1 — nested forward-result types were outside the facade

**Confirmed.** `ForwardWaterCalculationResult` and `ForwardSourceResult` were
root exports, but the source-resolution, blend, treatment, contribution-matrix,
and preparation-instruction types stored in their fields were not. Consumers
could run the documented calculation but could not safely discriminate or type
the complete audit graph without importing defining modules outside the stated
compatibility boundary.

The remediation exports that cohesive result graph, including its resolved and
unresolved union members, method/reason enums, matrix cells/statuses, and
instruction types. Public-API tests now consume those outputs solely through
package-root names and check both resolved and unresolved paths.

This decision does not indiscriminately export every transitive model. The
facade continues to support the curated built-in treatment ingredients rather
than the incomplete future generalized ingredient-authoring contract. Richer
reported profile provenance/property types are tracked as a separate 0.3 input
contract decision.

### F2 — P2 — source builds still report version 0.2.0

**Acknowledged; no version change in this remediation.** The reviewer correctly
observed that an installation made directly from `main` cannot use
`__version__` to distinguish unreleased API work from the published 0.2.0
artifact. The project deliberately changes distribution version metadata at
its release-version gate rather than on the first post-release development
commit. `docs/CONSUMER_API.md` prominently distinguishes the unreleased source
facade from published 0.2.0 and now states that `__version__` is distribution
identity, not a capability probe for a Git checkout. Consumers are directed to
released pinned distributions or exact commits, not a moving `main` branch.

### F3 — P3 — project-structure wording overstated the exports

**Confirmed.** The wording is narrowed and made specific: the facade exports
the selected proven input boundary and complete forward-result audit graph,
while later provenance/property and ingredient-authoring contracts remain
explicitly deferred.

### F4 — P3 — documentation inventory could drift from `__all__`

**Confirmed as a useful contract hardening.** The public API test now extracts
the explicitly marked inventory in `docs/CONSUMER_API.md` and requires it to
equal both the test's independent expected set and the package's `__all__`.

## Reviewer observations tracked for later 0.3 work

`SourceWaterProfile` preserves optional reported pH, disinfectant,
source-document, water-identity, alkalinity, hardness, TDS, conductivity, and
context fields whose construction types are not yet package-root exports. Those
fields do not currently feed the deterministic forward calculation, but their
public input/provenance boundary must be decided before 0.3 is considered
complete. The roadmap and consumer documentation now record that gap explicitly.
