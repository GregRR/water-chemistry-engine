## Findings

### HIGH — Target/reference comparison has no floating-point tolerance at criterion boundaries (CONFIRMED)

**File:** `packages/water-treatment-engine/src/water_treatment_engine/target_comparison.py`, `_compare_ion` (lines 172–249), reached from `compare_state_to_target`.

`_compare_ion` classifies a state against a target using bare `float` comparisons:

```python
if target_minimum is not None:
    minimum = float(target_minimum.magnitude)
    if actual_mg_per_liter < minimum:
        return ...BELOW_TARGET...
if target_maximum is not None:
    maximum = float(target_maximum.magnitude)
    if actual_mg_per_liter > maximum:
        return ...ABOVE_TARGET...
return ...WITHIN_TARGET..., deviation=0.0
```

There is no epsilon anywhere in this path. `actual_mg_per_liter` is not a source-reported literal — it is usually the output of blending's `fsum` over volume-weighted terms, or of treatment's mole/mass arithmetic, both of which are ordinary floating-point sums and are not guaranteed to reproduce a "nice" decimal exactly.

Confirmed with the real engine (not a mock), blending three sources that each report exactly 50.0 mg/L calcium in equal (1/3) proportion:

```
blended concentration (repr): 49.99999999999999
exactly 50.0?                 False
status vs. an exact 50.0 mg/L target: below_target
deviation:                    -7.105427357601002e-15 milligram / liter
```

Three water samples of identical chemistry, blended in equal parts, chemically must reproduce that exact chemistry. The engine instead reports the blend as failing an exact 50.0 mg/L target, with a "deviation" of roughly a femtogram per liter — a `fsum` rounding artifact of representing 1/3 in binary, not a chemistry result. The same mechanism affects any exact-ended range boundary (`minimum`/`maximum`), since it is the same comparison. It reproduces with any blend whose fractions aren't exact in binary (thirds, sevenths, most real-world multi-source ratios); it happens not to show up in the existing test suite because every current test blends sources using powers of two (0.5, 0.25, 0.75), which round exactly.

**Why it matters:** this is the calculation the checkpoint is explicitly built to answer — "does this water meet the target" — and priority review point 6 asks specifically about inclusive boundaries and signed deviation. A brewer or user who blends three sources of the same water 1:1:1 would see their otherwise-satisfied treatment reported as `NOT_SATISFIED`, with a deviation too small to be visible in any realistic display precision but large enough to flip the status enum. This is the opposite failure mode from "unknown remains unknown" — it presents a definite, wrong answer with no accompanying notice (the notices module only reacts to `ACTUAL_UNKNOWN` / `TARGET_UNSUPPORTED`, not to `BELOW_TARGET`/`ABOVE_TARGET`), so nothing in the current design would flag this to a user or a future UI as suspect.

**Suggested remediation:** compare with a small absolute tolerance on the mg/L scale (the codebase already has established precedent for this — `blending.py` uses `abs_tol=1e-9` for the fraction-sum-to-one check, `preparation_instructions.py` uses `rel_tol=1e-12, abs_tol=1e-12` for the volume-match check). Apply the same kind of tolerance to the `<`/`>` comparisons in `_compare_ion`, keeping the tolerance itself documented as a numerical-noise guard rather than a chemistry decision, so it doesn't get read later as "how close is close enough" domain policy.

### MEDIUM — `build_forward_notices` aligns sources with `blend_result.sources` by length only, not identity

**File:** `packages/water-treatment-engine/src/water_treatment_engine/forward_notices.py`, `_source_notices` (lines 65–118), specifically the guard at line 69.

```python
if len(source_resolutions) != len(blend_result.sources):
    raise ValueError(...)
...
for source_index, (resolution_result, blended_source) in enumerate(
    zip(source_resolutions, blend_result.sources, strict=True)
):
```

The only check that `source_resolutions[i]` actually corresponds to `blend_result.sources[i]` is that the two tuples have the same length. `build_forward_notices` is not a private helper — it's exported and exercised directly in `test_forward_notices.py` — so nothing in its contract prevents a caller from passing a `source_resolutions` tuple in a different order (or for different sources entirely) than the `blend_result` it's paired with. If that happens, the function will not raise; it will silently attach the wrong `source_name`/`source_index` to a `SOURCE_RANGE_MIDPOINT_USED` or `SOURCE_ION_UNRESOLVED` notice, because the notice takes its ion/method/reason from `resolution_result` but its display name from `blended_source`.

`calculate_forward_water` itself always builds both tuples from the same `sources` argument in the same order, so this isn't live today. It's the kind of contract that a 0.3 web layer — which will need to reconstruct or re-serialize these tuples across a request boundary — could violate without any test catching it, and the resulting notice would misattribute an assumption/warning to the wrong named source in the exact audit trail this feature exists to provide.

**Suggested remediation:** verify pairing by content, not just count — e.g., assert `resolution_result.state == blended_source.state` (or thread a shared identifier) before trusting the zip, or change the signature to accept a single sequence of paired `(resolution, blended_source)` tuples so misalignment can't be expressed at all.

### MEDIUM — `IonContribution` doesn't normalize its stored unit; the new contribution-matrix sums assume it's already mg/L

**Files:** `treatment_stoichiometry.py`, `IonContribution.__post_init__` (lines 26–41); `contribution_matrix.py`, `known_treatment_contribution_sum` (lines 129–137, reading `cell.contribution.magnitude` at line ~220 in the surrounding property).

`DerivedIonConcentration.__post_init__` (chemical_state.py) is deliberately defensive: it validates convertibility to mg/L and then re-writes its own field with `object.__setattr__` so the stored quantity is always literally `Q_(magnitude, "milligram / liter")`. `IonContribution.__post_init__` only does the first half — it validates that `.to("milligram / liter")` succeeds but never normalizes the stored `concentration` to that unit:

```python
def __post_init__(self) -> None:
    try:
        normalized = self.concentration.to("milligram / liter")
    except Exception as exc:
        raise ValueError(...) from exc
    if normalized.magnitude < 0:
        raise ValueError(...)
    # normalized is discarded; self.concentration is left as constructed
```

`contribution_matrix.py`'s `known_treatment_contribution_sum` then reads `cell.contribution.magnitude` directly (no `.to(...)` call) and wraps the `fsum` result in a hard-coded `"milligram / liter"` unit. Today this is harmless, because the only production constructor, `calculate_ion_contributions`, always builds the quantity as `Q_(ion_mass_mg / volume_liters, "milligram / liter")` already. But the type itself doesn't enforce that, and nothing stops a future ingredient calculation, a test fixture, or a 0.3-era refactor from constructing an `IonContribution` in a different (but still pint-convertible) unit, such as grams per liter — which would pass `__post_init__` silently and then be summed as if it were 1000x smaller than it is. The source-contribution side of the same matrix doesn't have this gap: `BlendIonContribution.weighted_contribution` is always built as mg/L in `blending.py` and that module doesn't rely on an un-enforced invariant to read it back.

**Suggested remediation:** normalize `IonContribution.concentration` in `__post_init__` the same way `DerivedIonConcentration` does (`object.__setattr__(self, "concentration", normalized)`), or, failing that, have `contribution_matrix.py` call `.to("milligram / liter")` before reading `.magnitude` rather than trusting the constructor.

### MEDIUM — Two implementations of "does this treatment follow from this blend" disagree on strictness

**Files:** `contribution_matrix.py`, `build_contribution_matrix` (lines 262–280, specifically 277–280); `preparation_instructions.py`, `build_preparation_instructions` (lines 117–140, specifically 134–137).

Both functions independently guard the same invariant — that the `TreatmentApplicationResult` passed in actually started from the `WaterBlendResult` passed in — and both check volume equality, but differently:

```python
# contribution_matrix.py — exact Quantity equality
if treatment_result.water_volume.to("liter") != blend_result.total_volume.to("liter"):
    raise ValueError(...)

# preparation_instructions.py — tolerance-based
treatment_liters = float(treatment_result.water_volume.to("liter").magnitude)
blend_liters = float(blend_result.total_volume.to("liter").magnitude)
if not isclose(treatment_liters, blend_liters, rel_tol=1e-12, abs_tol=1e-12):
    raise ValueError(...)
```

In `calculate_forward_water` both are always fed the literal same `blend_result.total_volume` object, so the two checks currently agree in practice. But this is the same class of problem as the HIGH finding above, in miniature and in the guard code rather than the chemistry: two sibling modules re-implement the same "is this really the linked blend" check with different strictness, so a future caller (or a fix to one that isn't mirrored in the other) could make one accept an input the other rejects, for what's supposed to be one shared contract.

**Suggested remediation:** factor this into one shared helper (e.g., in a small internal module both `contribution_matrix.py` and `preparation_instructions.py` import), so the strictness decision is made once.

### LOW — Aggregate target status treats "a pH target exists" as unsafe, rather than "pH wasn't evaluated"

**File:** `target_comparison.py`, `_profile_status` (lines 252–277, condition at line 266).

```python
if ph_comparison is not None or any(
    comparison.status in (ACTUAL_UNKNOWN, TARGET_UNSUPPORTED)
    for comparison in ion_comparisons
):
    return INDETERMINATE
```

This is correct today only because `TargetPHComparisonStatus` has exactly one member, `NOT_CALCULATED` — so "a pH comparison exists" and "pH wasn't evaluated" happen to be the same fact. If a later engine version adds a computed pH status, this line would need to change in lockstep to check `ph_comparison.status is NOT_CALCULATED` specifically; as written, a fully-satisfied, fully-computed result (including a matching, computed pH) would still report `INDETERMINATE` forever, silently, because nothing here is coupled to the enum's shape.

**Suggested remediation:** check the status value explicitly (`ph_comparison is not None and ph_comparison.status is TargetPHComparisonStatus.NOT_CALCULATED`) now, even though it's redundant today, so the code fails to compile-time-obviously rather than silently when the enum grows.

### LOW — Forward-result notices only reflect the final target comparison, not the source- or blend-stage ones

**File:** `forward_notices.py`, `_target_notices` (lines 148–199) and `build_forward_notices` (lines 202–220); `forward_calculator.py`, `calculate_forward_water` (the `notices = build_forward_notices(..., final_target_comparison)` call).

`ForwardWaterCalculationResult` exposes a `target_comparison` on every `ForwardSourceResult` and a separate `blend_target_comparison`, but `build_forward_notices` only ever receives `final_target_comparison`. `TARGET_CRITERION_UNSUPPORTED` reasons are a property of the target profile alone, so they'd be identical at every stage and aren't actually lost. `TARGET_ACTUAL_UNKNOWN` reasons can differ by stage (a source missing an ion vs. the final blend/treatment result), so a caller inspecting `source_results[i].target_comparison` or `blend_target_comparison` directly gets no corresponding notice and has to re-derive the same "actual unknown" reasoning the notices module already knows how to produce, for those two stages, itself.

This may be intentional — the design-doc update frames notices around "the forward-result," i.e. the final state — but it's worth confirming deliberately rather than by omission, since it's exactly the kind of case priority 9 asks to check ("both missing warnings and noisy/misleading warnings").

**Suggested remediation:** either generate notices for all three comparison stages (tagging each with which stage it came from), or state explicitly in the module docstring that notices are scoped to the final result only, so a 0.3 UI doesn't reasonably assume otherwise.

### LOW — No test exercises the `NOT_SATISFIED` vs. `INDETERMINATE` precedence

**File:** `test_target_comparison.py`; corresponding logic in `_profile_status` (lines 252–277).

`_profile_status` checks for `BELOW_TARGET`/`ABOVE_TARGET` first and only falls through to the `INDETERMINATE` check if none are present — meaning a profile with one ion failing and a separate ion unknown/unsupported (or a pH target present) correctly reports `NOT_SATISFIED`, not `INDETERMINATE`. This ordering is exactly the kind of aggregate-status subtlety priority 6 calls out, and none of the ten `test_target_comparison.py` cases construct a profile with both conditions present at once; an accidental reordering of the two `if` blocks would change this precedence silently.

**Suggested remediation:** add one test with a target profile containing both a definitely-failing ion and an unknown/unsupported one, asserting the overall status is `NOT_SATISFIED`.

### LOW — None of the five new test modules use property-based testing, despite the project's own precedent

**Files:** `test_contribution_matrix.py`, `test_forward_calculator.py`, `test_forward_notices.py`, `test_preparation_instructions.py`, `test_target_comparison.py` (all new in this range); compare `test_blending.py` (pre-existing), which already uses `hypothesis` for exactly this class of invariant (source-order independence, sum properties).

`hypothesis` is a declared dev dependency and already exercised in the codebase, but every test added in this range is example-based. Two invariants introduced in this range are natural, currently-unverified candidates:

- `IonContributionMatrixRow.known_source_contribution_sum == blend_concentration` whenever every positive-volume source is resolved, for arbitrary source counts, volumes, and concentrations.
- In `target_comparison`, deviation sign should always match status (negative iff `BELOW_TARGET`, positive iff `ABOVE_TARGET`, exactly zero iff `WITHIN_TARGET`), across randomized bounds and actual values, including boundary-equal cases.

The second property is precisely the one the HIGH finding above violates — a property test built from that description would have caught it directly, rather than requiring hand construction of a 1/3-fraction blend to surface it.

**Suggested remediation:** add `hypothesis`-based tests for at least these two invariants, following the pattern already established in `test_blending.py`.

## Verdict

**REMEDIATION REQUIRED BEFORE 0.3.**

The HIGH finding is a confirmed, reproducible defect in the exact feature this checkpoint is meant to certify — target/reference comparison — and it fails in the ordinary case (any non-power-of-two blend ratio), not an exotic one. Building a web UI on top of it now would mean shipping a status indicator that can silently and incorrectly tell a user their water doesn't meet target when it does, with no notice or hedge anywhere in the result to suggest the number is suspect. The fix itself is narrow and has direct precedent already in the codebase (`isclose` with a small `abs_tol`), so this shouldn't meaningfully delay 0.3 — but it should land, with a regression test at a non-exact fraction, before comparison results are surfaced to anyone.

Everything else found is MEDIUM or LOW: latent contract/robustness gaps that aren't live bugs today (notice misattribution requires misuse the current code never exercises; the unit-normalization gap requires a constructor path that doesn't exist yet; the duplicated volume check currently agrees by construction), plus test-coverage gaps. None of them block 0.3 on their own, but the MEDIUM items are worth fixing alongside the HIGH one since they're touching the same files, and the missing property tests would have caught the HIGH finding for free.

The rest of the reviewed surface — unknown-vs-zero distinction, zero-volume source exclusion, treatment auditability when a starting concentration is unresolved, qualified-range/ND handling remaining unsupported rather than guessed, and the deterministic-vs-deferred-pH boundary — held up under inspection and against the existing test suite; no separate findings are recorded for it.
