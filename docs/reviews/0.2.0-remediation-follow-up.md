### 4.2 Original HIGH finding — independent reproduction (checklist §2)

**A NaN treatment mass can no longer produce a NaN final concentration**, because it is rejected at the earliest possible point: `TreatmentAddition(ingredient=..., mass=Q_(float("nan"), "gram"))` raises `ValueError: Treatment addition mass must be finite.` immediately at construction, before any `TreatmentAddition` object bearing that mass can be built, let alone passed to `calculate_forward_water`. I confirmed this is not merely a happy-path assumption by trying to construct exactly the object the original finding used to reach `calculate_forward_water` and observing the exception directly.

**Both required layers of protection are independently confirmed working:**

1. **Domain constructors reject invalid values before calculation** — demonstrated above for every listed type.
2. **`target_comparison._compare_ion` itself refuses non-finite actual concentrations and target bounds, even when a frozen object's constructor invariant is deliberately bypassed.** I reproduced this exactly as the task specified, using `object.__setattr__` to corrupt an already-constructed, otherwise-valid `DerivedIonConcentration` (simulating e.g. a future deserialization path or a regression elsewhere that skips the constructor):
   ```
   corrupted = DerivedIonConcentration(ion=Ion.SODIUM, concentration=Q_(1.0, "milligram/liter"))
   object.__setattr__(corrupted, "concentration", Q_(float("nan"), "milligram/liter"))
   ```
   Comparing a state built from this corrupted object against a target now raises `ValueError: Actual ion concentration must be finite for comparison.` rather than silently returning any status. I repeated the same bypass against the **target** side (`object.__setattr__` on the target's stored `IonConcentration.value` to `+inf`) and got the symmetric `ValueError: Target ion concentration must be finite for comparison.` — confirming the fix checks both operands, not just the one the original public repro happened to use.

   I confirmed this defense-in-depth check fires correctly across **all four target-criterion kinds** named in the task (exact, range, upper-bound, lower-bound): in each case, a corrupted NaN actual value against that kind of target raises the same `ValueError` rather than returning `WITHIN_TARGET` or any other status. This exactly matches the maintainer's own new regression tests (`test_comparison_defensively_rejects_non_finite_actual`/`_target` in `tests/test_target_comparison.py`), which use the identical `object.__setattr__` bypass technique — independently confirming the maintainer tested for precisely this scenario, not just the constructor-level happy path.

No combination of exact/range/upper-bound/lower-bound target, actual, or bound value can currently produce `WITHIN_TARGET` or `SATISFIED` from a non-finite input at any layer I could reach. This is the original HIGH finding, fully closed.

### 4.3 Stoichiometry validation (checklist §3)

`IonStoichiometry.coefficient` now correctly:

- accepts a genuine positive `int` (confirmed: `coefficient=2` constructs normally);
- rejects `0` and negative integers with `ValueError: Ion stoichiometric coefficient must be positive.`;
- rejects `True`/`False` with `TypeError: Ion stoichiometric coefficient must be an integer.` (Python's `bool` is a subclass of `int`, so this required — and got — an explicit `isinstance(x, bool)` check ahead of the `isinstance(x, int)` check; I confirmed the ordering is correct by testing both `True` and `False` directly);
