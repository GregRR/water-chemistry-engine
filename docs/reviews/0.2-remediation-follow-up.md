**Extended adversarial fuzzing** (independent of the shipped Hypothesis tests, 8,000 additional randomized trials):

- 5,000 trials blending 1–9 sources of identical chemistry at random volumes (0.001–1000 L, random concentration 0.001–1000 mg/L): 5,000/5,000 came back `WITHIN_TARGET` with exactly zero deviation against an exact target equal to that chemistry.
- 3,000 trials blending two sources of *different* concentrations at random volumes, compared against random targets: 0 cases where a real difference greater than 1e-6 mg/L was masked as `WITHIN_TARGET`, and 0 sign mismatches between `deviation` and status.

The fix generalizes well beyond the reported case and does not trade the original false-positive problem for a false-negative one.

## Per-finding status

### HIGH — Target comparison had no floating-point tolerance at boundaries: **RESOLVED**

`target_comparison.py` now compares `actual` against `minimum`/`maximum` with `math.isclose(rel_tol=0.0, abs_tol=1e-9)` (mg/L) before classifying `BELOW_TARGET`/`ABOVE_TARGET`; a difference within that tolerance falls through to `WITHIN_TARGET` with `deviation` set to the literal `0.0`, not the raw (nonzero) float difference. The tolerance is fixed at 1e-9 mg/L regardless of the target's scale — several orders of magnitude larger than the `~7e-15` noise it needs to absorb, and several orders of magnitude smaller than any realistic chemistry/reporting precision (typically ≥0.01 mg/L). Both the docstring on `TargetIonComparison.deviation` and the module docstring on `compare_state_to_target` now say explicitly that this is a numerical-noise guard, not a domain tolerance — addressing the original remediation's specific concern that this not get mistaken later for "how close is close enough" policy. Confirmed empirically above, including that it doesn't mask genuine violations.

### MEDIUM — `build_forward_notices` paired sources by length only: **RESOLVED**

`_source_notices` now raises unless `resolution_result.source_profile.name == blended_source.name` and `resolution_result.state == blended_source.state` for every paired entry, before the zip is trusted for anything. A dedicated regression test (`test_source_resolution_order_must_match_blend_sources`) swaps the pairing order and confirms the `ValueError`. I traced `calculate_forward_water`'s construction path and confirmed both tuples are built from the same `(source, resolution)` pairs in the same order, using the literal `resolution.state` object for both — so the added check cannot spuriously reject the normal call path (also confirmed by the full test suite passing).

One narrow, non-blocking residual: the check is by *content* (name + state), not identity. Two distinct blend sources that happened to share both an identical name and an identical fully-resolved chemical state could still be silently swapped. This is not a live concern — such sources are chemically indistinguishable, so a swap between them can't misattribute anything a user or UI would notice — but it's worth knowing this is a content-equality guard rather than an identity guard if a future caller ever needs a stronger guarantee (e.g., two genuinely different sources that happen to report identical numbers).

### MEDIUM — `IonContribution` didn't normalize its stored unit: **RESOLVED**

`IonContribution.__post_init__` now does `object.__setattr__(self, "concentration", Q_(magnitude, "milligram / liter"))` after validating convertibility — the same pattern `DerivedIonConcentration` already used. `contribution_matrix.py`'s `known_treatment_contribution_sum` no longer relies on an unenforced constructor invariant. New regression test `test_ion_contribution_normalizes_convertible_units_to_mg_per_liter` constructs a `0.001 gram/liter` contribution and asserts it comes out as `1.0 milligram/liter` — exactly the scenario the original finding described as silently wrong before this fix.

### MEDIUM — `contribution_matrix.py` and `preparation_instructions.py` disagreed on strictness: **RESOLVED**

Both now call a single shared helper, `_workflow_validation.require_treatment_matches_blend`, which checks `initial_state` equality and then volume equality via `isclose(rel_tol=1e-12, abs_tol=1e-12)` — the more permissive of the two original checks, now used everywhere. Its docstring states plainly that the tolerance "tolerates only floating-point representation noise" and is "not a domain-level allowance for treating different batch volumes as equivalent." `test_workflow_validation.py` covers all three cases directly: mismatched initial state rejected, sub-picoliter rounding noise (5e-13 L) allowed, and a material difference (1e-6 L) rejected. I grepped the rest of `src/` and confirmed no other independent reimplementation of this check remains.

### LOW — Aggregate status treated "pH target exists" as unsafe rather than "pH not evaluated": **RESOLVED**

`_profile_status` now checks `ph_comparison.status is TargetPHComparisonStatus.NOT_CALCULATED` explicitly rather than mere presence of a `ph_comparison` object, so this won't silently break the day the pH status enum grows a second member.

### LOW — No test for `NOT_SATISFIED` vs. `INDETERMINATE` precedence: **RESOLVED**

`test_definite_failure_takes_precedence_over_indeterminate_criterion` constructs a profile with one definitely-failing ion and one unknown ion and asserts the overall status is `NOT_SATISFIED`. Passes, and the underlying `_profile_status` code correctly checks `BELOW_TARGET`/`ABOVE_TARGET` before the indeterminate branch (unchanged ordering, now locked in by a test).

### LOW — Forward notices only reflect the final target comparison: **RESOLVED (confirmed as intentional and now documented)**

This was flagged as a design question, not a defect, and the remediation answers it: `forward_notices.py`'s module docstring and `build_forward_notices`'s docstring both now state explicitly that target notices are scoped to the final treated-water comparison and that source-/blend-stage comparisons "remain available on their own structured results" rather than being duplicated as notices. That's internally coherent — `ForwardWaterCalculationResult` still exposes `source_results[i].target_comparison` and `blend_target_comparison` directly for a caller that wants them at those stages.

### LOW — No property-based tests in the five new modules: **PARTIALLY RESOLVED**

Hypothesis tests were added, but only to two of the five originally-flagged modules — and they're exactly the two invariants the original finding named as the highest-value additions:

- `test_contribution_matrix.py::test_known_source_contribution_sum_matches_resolved_blend` — 1 to 6 sources, random concentrations (0–1000 mg/L) and volumes (0.001–1000 L), asserts `known_source_contribution_sum == blend_concentration`.
- `test_target_comparison.py::test_blending_identical_chemistry_preserves_exact_target_status` and `test_exact_target_deviation_sign_matches_status` — random concentrations/volumes and random actual/target pairs, respectively; the first is effectively a generalized property-based version of the exact HIGH-finding regression, the second checks the deviation-sign invariant across the whole status space.

`test_forward_notices.py`, `test_forward_calculator.py`, and `test_preparation_instructions.py` still have no Hypothesis coverage — the property-testing gap remains for those three. For 0.2 specifically, the two invariants that mattered most (the ones tied to the HIGH finding and to contribution accounting) are now covered; the broader "the whole new surface should get some property testing" aspiration is only half done.

## New issues introduced by the remediation

None at HIGH or MEDIUM severity. I looked specifically for: false negatives from the new tolerance (none found, see fuzzing above), spurious rejections from the new pairing/linkage checks on the normal call path (traced through `calculate_forward_water` and confirmed by the full suite), and any second, un-migrated copy of the volume/state check left behind (none found via grep). The one LOW/optional item is the content-vs-identity pairing note under the source/notice finding above; it's a residual characteristic of the chosen fix, not something newly broken, and doesn't require action for 0.2.

## Verdict

**SAFE TO PROCEED TO 0.2 RELEASE AUDIT.**

The HIGH finding is resolved with a fix that matches the codebase's own precedent (a small, explicitly-documented absolute tolerance) and holds up under both the shipped regression/property tests and 8,000 additional independent randomized trials in both directions (no false positives, no false negatives). All three MEDIUM findings are resolved with real code changes backed by passing regression tests, not just documentation. Three of the four LOW findings are fully resolved; the fourth (property-test coverage) is partially resolved — the two invariants that actually mattered are covered, three test modules still have none. That's a reasonable gap to carry into a release audit rather than a reason to hold the milestone.
